THE ONE THAT MATTERED MOST: BOTH READERS FOUND IT

 1. THE RECOMMENDATION CONTRADICTED ITSELF. In the first version DEMO-7 was ranked FIRST, under "open, not blocked".
    A few lines below, DEMO-9's reasons said: "issuelinks shows 2 open items waiting on it: DEMO-7, DEMO-10".
    The cause: whether an item is blocked was decided from the item's OWN record only. DEMO-7's copy was 11 days
    old and did not hold the link yet. DEMO-9's fresher record did. Which items WAIT on an item was read from both
    ends; which items BLOCK it was not. Only the stale warning kept DEMO-7 from being "start here". Had its copy
    been two hours older than DEMO-9's instead of eleven days, it would have been offered as the item to start,
    with confidence high, while a fresher record said it was blocked.
    Reader 1 found it by checking the printed facts against the rules by hand. No test of mine had: every test
    made the two ends of a link agree.
    DONE: both ends of a link are read. An item is blocked if either record says so, and the reason says which
    record showed the link. Four tests and four planted bugs. The run now shows the case with DEMO-12.

WHAT ELSE READER 2 FOUND, AND WHAT WAS DONE

 2. A blocker's own record was always believed, even when it was OLDER than what the blocked item showed of it.
    DONE: if the two copies of a blocker's status disagree about whether it is done, the item stays blocked,
    confidence falls, and the reason gives both copies with their times.
 3. A link was taken to block only if its type is named exactly "Blocks". On a site where that type is renamed,
    nothing would ever be blocked, and the recommendation would say "Blocked: none" in silence.
    DONE IN PART: the site's link types are copied. If none is named "Blocks", the recommendation says in capitals,
    at the top, that nothing can be shown as blocked. It still does not recognise a renamed type.
 4. The real-run script copied a second time OVER the records it had just ranked, so the saved recommendation would
    not have matched the saved records. It also printed "DONE" when the snapshots differed.
    DONE: the second copy goes to a temporary file. The script stops if the snapshots differ, and saves them.
 5. "Every one was a GET" COULD NOT BE FALSE. The line was written from a list my own code filled with the word
    "GET". So the log line, a check in the run record and a test were all saying nothing.
    DONE: for a real Jira the method, and whether the request carried a body, are read back from each request as it
    was built. A test changes how a request is built and sees the line change. For the fake Jira the output says
    plainly that the line proves little there.
 6. Refreshing against a real Jira: a deleted key would have made the whole refresh fail, an item moved to another
    project would have been merged under its new key, and records were matched by key, not by Jira's id.
    DONE: each named item is asked for by itself; "not found" means gone; an item answered under another key is
    reported and taken out; records are matched by id. Tested on the fake Jira only. NOT TRIED ON THE REAL ONE.
 7. The snapshot claims said more than two listings can show, and a refresh was silent about other items that had
    changed in Jira.
    DONE: the wording says the two listings agree, and that a search can be behind. A refresh now lists the items
    whose last-updated time in Jira is no longer the one in their copy.
 8. Privacy. Names chosen by a site's administrators could carry characters that break a Markdown table; times
    kept the site's time zone; my notes said titles were "not asked for" when Jira sends linked items' titles anyway.
    DONE: those names are stripped to plain characters, times are rewritten in UTC, and the notes say what Jira
    sends and what is dropped.
    NOT CHANGED: the "site fingerprint" in the records is a short hash of the site's name, so a guessed name can be
    confirmed. Every earlier Jira quest of mine keeps the same fingerprint.
 9. Checks in the run record that could not fail: the fake Jira's file compared before and after a ranking that is
    never given that file; "no title is copied" tested only that the program printed that sentence; the check that
    every reason names a field looked at four kinds of line out of a dozen.
    DONE: the records file and everything printed are searched for the fake Jira's titles, names and account ids;
    the reason check covers twelve kinds of line; what the fake Jira can and cannot show is said in the record.
10. Tests: the byte-for-byte test ran twice in one process; a few behaviours were untested.
    DONE: it now runs in separate processes with different hash seeds. Tests were added for the rest.
    NOT DONE: no test for a redirect being refused, or for the search of the output for credentials.
11. Things about a real Jira that are assumed: that it lists priorities highest first; that a token with limited
    scope uses the same address.
    PARTLY ANSWERED BY THE REAL RUN: my site listed Highest, High, Medium, Low, Lowest, in that order. The rest stands.
12. Smaller ones, all done: a due date is now said to be compared with the UTC date; two keys differing by a
    leading zero are ordered by a rule; a records file with a value of the wrong shape stops the ranking cleanly;
    a blocked item's confidence gives its reason; an empty page that claims more is refused and cannot loop.
